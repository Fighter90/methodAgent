# Автопроверка, судья и автоисправление

Пакет `src/app/validation/` проверяет программу и комплект 27 правилами V-01…V-27 (`rules.py`): 20 правил объединены в 10 блокирующих проверок, ещё 7 дают только предупреждения. Правила — чистые функции над `ProgramDoc`, 23 реализованы кодом, 4 смысловых (V-21, V-22, V-26, V-27) — эвристиками, которые уточняет модель-судья (`judge.py`). То, что можно исправить без модели, чинит `repair.py`; примеры кода выполняются в песочнице (`sandbox.py`); оригинальность относительно референсов считается по 8-граммам (`ngrams.py`); `report.py` собирает отчёт агента: статусы правил, блокирующие проверки, матрицу «РО × средство оценивания», действия методиста и предложения по пунктам «!». От отчёта зависят утверждение каркаса, назначение экспертов, отправка на утверждение и индекс готовности.

## Статусы и этапы

- Статусы правила: `pass`, `warn`, `fail`. Правило без блокирующей проверки (`check is None`) никогда не возвращает `fail`: `run_rules` переводит такой результат в `warn`. Исключение внутри правила не роняет отчёт — правило получает `warn` «Правило не выполнено: <тип ошибки>».
- Этап `skeleton` выполняет только правила из `SKELETON_RULES`: V-01…V-08, V-10, V-12, V-13, V-15, V-21, V-22, V-27 (15 правил). Этап `kit` — все 27.
- Каждый результат хранит сообщения и ссылки на узлы графа (`nodes`), чтобы из отчёта перейти к элементу.

Замечания по реализации:

- V-20 даёт `fail` только при `last_edit_check.ok == false`, но `workflow.edit` всегда записывает `ok: True` (и для отклонённой правки — с `rejected: True`, после чего документ откатывается к снимку). Регрессии правки отсекаются самим `edit` (откат и ошибка `EDIT_REJECTED`), поэтому в отчёте V-20 на практике всегда проходит.
- V-16 не только проверяет, но и меняет документ: источник, найденный в реестре, помечается `confirmed = True`.

## Блокирующие проверки и счётчики

`CHECK_TITLES` (номер → проверка, правила):

| № | Проверка | Правила |
|---|---|---|
| 1 | Арифметика часов | V-01…V-07 |
| 2 | Полнота шаблона | V-08, V-09 |
| 3 | Календарная выполнимость | V-10 |
| 4 | Поля для людей | V-11 |
| 5 | Покрытие компетенций | V-12, V-13 |
| 6 | Привязка оценивания к РО | V-14 |
| 7 | Источники | V-15, V-16 |
| 8 | Оригинальность | V-17 |
| 9 | Измеримость заданий | V-18, V-19 |
| 10 | Точечная правка без регрессий | V-20 |

**«10/10 блокирующих».** `report.blocking_status` считает проверку пройденной, если ни одно её правило не имеет статуса `fail` (`warn` допустим). На этапе `kit` `blocking_passed` — число пройденных из 10, `blocking_total = 10`. На этапе `skeleton` учитываются только проверки 1, 2, 3, 5, 7, и знаменатель равен 5. `workflow.blocking_ok` требует отчёт этапа `kit` и `blocking_passed == blocking_total`; от этого зависят `assign_expert` и `submit`, а `readiness` складывает число пройденных проверок с принятыми модулями.

**«26/27 правил».** В ответе автопрогона (`_auto_response` в `src/app/programs/router.py`) `rules_passed` — число правил со статусом, отличным от `fail` (то есть `pass` и `warn` считаются пройденными), `rules_total` — число правил в отчёте (27 на этапе комплекта). Так как правила без блокирующей проверки не бывают `fail`, «26/27» означает, что одно блокирующее правило не прошло. Там же отдаётся строка `blocking_checks` вида `10/10` и список `failed_rules`.

## Судья (`judge.py`)

- Вызывается в конце `generate_kit`, если `llm_judge_enabled`, модель включена и суточный лимит не исчерпан.
- Вход — сокращённое представление программы (`_view`): название, тип, объём, аудитория, входной уровень, ожидание заказчика, цель, РО, модули и темы, начало аннотаций двух модулей, три последние заметки агента. Сокращение нужно, чтобы ответ рассуждающей модели укладывался в 4096 токенов.
- Вызов: `complete_json(skill='judge', role='judge', temperature=0.0, max_tokens=4096)`, схема `JudgeOut{verdicts: [{rule, status: pass|warn, messages}]}`. Системный промпт задан в коде (а не в `skills/validate/SKILL.md`): по каждому правилу статус и 0–3 конкретных замечания, только при явном нарушении.
- Результат — `doc.kit.judge`: для правил с `warn` и непустыми замечаниями до 3 замечаний.
- `merge(doc, report)` при сборке отчёта этапа `kit`: правило со статусом `pass` становится `warn`, к сообщениям добавляются «Судья: …». Судья не снимает замечаний кода и не может сделать правило блокирующим.
- Ошибка судьи (нет ответа, лимит, бюджет) — замечания кода остаются как есть.

## Автоисправление (`repair.py`)

`repair(doc, rules)` выполняется в `generate_kit` до двух раз, пока есть правила с `fail` (после каждого прохода разделы и отчёт пересобираются), а в режиме `auto` — ещё и при утверждении каркаса. Модель не используется. Возвращает журнал исправлений.

| Правило | Исправление |
|---|---|
| V-19 | Убирает повторяющиеся варианты (добирая до 4 вариантами «Другой вариант N»); ключ вне диапазона → 0 |
| V-18 | Задание без критериев или с нулевыми баллами получает рубрику 4 + 4 + 2 |
| V-14 | Задания — РО их темы; вопросы без валидного РО — РО из тем модуля (выбор по `hash(q.id)`) |
| V-13, V-14 | РО с одним средством добавляется в итоговое задание; `cover_outcomes` добавляет вопрос в тест модуля (верный ответ — формулировка РО, дистракторы — РО других модулей) или включает РО в задание семинара; если объём теста задан в запросе, вопрос заменяет «лишний» вопрос по РО, который и так проверяется несколькими вопросами (`_spare_question`) |
| V-09 | `_fix_materials`: название лекции приводится к теме УТП; если слайдов нет, они собираются из описания темы и плана лекции для модулей из запроса (или первого модуля) с пометкой о вычитке |
| V-17 | `_drop_reference_overlap`: из аннотаций, текстов тем и описаний тем удаляются предложения, имеющие общие 8-граммы с референсом |
| V-08, V-11 | Разделы шаблона пересобираются `build_sections` (пустые заполняются, реквизиты возвращаются в поля) |
| V-16 | Неподтверждённый источник помечается «[не подтверждено]» |

Ошибки, которые не удалось исправить, остаются в отчёте для методиста.

## Песочница (`sandbox.py`)

`run_detailed(code)` возвращает `{ok, mode, error, stdout, seconds}`:

1. Пустой код — `mode: skip`.
2. Код, обращающийся к системе (`os`, `sys`, `subprocess`, `socket`, `pathlib`, `importlib`, `threading`, `asyncio`, `urllib`, `http`, `pickle` и др.), дандер-имена, вызовы `eval`, `exec`, `compile`, `open`, `getattr`, `setattr`, `globals`, `locals`, `vars`, `breakpoint` — `mode: skip` с пометкой «проверьте вручную» (`ok` остаётся `true`).
3. Код с тяжёлыми библиотеками (`pandas`, `numpy`, `matplotlib`, `seaborn`, `sklearn`, `requests`, `sqlalchemy`) или `sqlite3` — только проверка синтаксиса `compile` (`mode: syntax`).
4. Иначе — отдельный процесс `python -I -c` во временном каталоге: таймаут 10 с, лимиты процессора 10 с, памяти 512 МБ и 64 процессов (на POSIX), окружение только с `PATH` и несуществующими прокси (сеть недоступна), на stdin подаётся `5\n5\n5\n`. Ненулевой код возврата — ошибка с последней строкой stderr; stdout сохраняется до 800 символов.

Лимиты ресурсов (`_limits`) пробуются по одному: если платформа не даёт их понизить (на macOS `RLIMIT_AS` отвергается — hard limit `RLIM_INFINITY` непривилегированному процессу понижать нельзя), лимит пропускается, а пример всё равно запускается. `run_detailed` сообщает об этом честно: в результате — `applied_limits` и `skipped_limits`, списки имён констант `resource`, которые удалось и не удалось установить (проверяются заранее пробным fork-процессом `_probe_limits`, чтобы не трогать лимиты самого приложения); для режимов `skip` и `syntax` оба списка пустые. Поэтому `make check` проходит и на macOS, а отчёт песочницы показывает, какие ограничения реально действовали.

Использование: `workflow._fix_examples` (исправление моделью или удаление упавших примеров до проверки), правило V-24 (`check_examples`, первые 12 примеров), отчёт песочницы `extras.sandbox_report` (до 20 примеров, версии библиотек, устаревшие конструкции) и метрика `code_ok_share` в `workflow.quality`.

## Оригинальность (`ngrams.py`)

- `_tokens` — слова из латиницы, кириллицы и цифр в нижнем регистре; `ngrams(tokens, 8)` — множество 8-грамм.
- `overlap_share(text, reference)` — доля 8-грамм текста, встречающихся в референсе. Для V-17 сравнивается только содержание: разделы, кроме обязательных формул шаблона и реквизитов НПА (`TEMPLATE_FORMULA_KEYS`), программы модулей, вопросы, задания, планы и слайды лекций. Референс — `text_sample` приложенных файлов. Порог — 5 %.
- `similarity(a, b)` — сходство названий тем через `difflib.SequenceMatcher` (V-25).

## Отчёт агента (`report.py`)

`build_report(doc, stage)` возвращает `Report`:

| Поле | Содержание |
|---|---|
| `rules` | результаты правил этапа (с замечаниями судьи на этапе `kit`) |
| `blocking_passed`, `blocking_total` | см. выше: из 10 (комплект) или из 5 (каркас) |
| `coverage` | матрица «РО × средство»: компетенция, код и текст РО, темы, число элементов каждого средства, число средств. На каркасе — плановые средства (`Контроль Мn`, `Сем. Мn`, `ИА`) |
| `actions` | до 20 действий: модули из резерва («нужна доработка эксперта»), замечания судьи, до 3 сообщений каждого `fail`, до 2 сообщений каждого `warn` |
| `proposals` | предложения по пунктам «!» с признаком `decided`: V-22 — переформулировка РО «Объясняет и применяет на примере: …»; V-21 — поменять темы местами; V-10 — по одному предложению на вариант календаря; V-27 — сформулировать результаты как начальный уровень; V-15 (`warn`) — сверить коды ТФ с реестром Минтруда |
| `assumptions` | допущения агента с подписью поля и пометкой «принято агентом» |

Отчёт пересобирается после каждого изменения каркаса или комплекта (`recompute`, `decide`, `edit`, `generate_kit`).

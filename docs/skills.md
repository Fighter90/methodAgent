# Навыки агента

Навык — это каталог `src/app/skills/<имя>/` с инструкцией `SKILL.md` (YAML-заголовок с параметрами вызова модели и текст системного промпта), входной схемой `schema_in.json` и, если навык выполняется кодом на Python, модулем `run.py`. Каталог навыков читает `src/app/skills/base.py`; администратор может переопределить часть параметров через интерфейс без пересборки образа. Модель используют только `intake`, `skeleton`, `content` и `review_assist`; у каждого из них есть детерминированный резерв, поэтому без модели (режим `fixtures`, нет ключа, исчерпан лимит или бюджет) агент собирает полный, хотя и шаблонный, комплект. Остальные навыки (`classify`, `clarify`, `hours_solver`, `export`, `workflow`, `repair`, `validate`) реализованы кодом в других пакетах, а их `SKILL.md` служит описанием и источником параметров.

## Загрузка навыков (`base.py`)

- `SkillSpec` — неизменяемая запись: `name`, `description`, `model_role`, `temperature` (по умолчанию 0.2), `max_tokens` (2000), `timeout_s` (60), `retries` (2), `instruction` (тело `SKILL.md` после заголовка), `path`.
- `_parse(path)` делит файл по `---` на заголовок и тело и читает заголовок `yaml.safe_load`. Поля `input`/`output` в заголовке есть, но кодом не читаются; файлов `schema_out.json` в каталогах нет.
- `original_skills()` — все `skills/*/SKILL.md` в алфавитном порядке.
- `load_skills()` (кэш `lru_cache`) — исходные навыки с переопределениями администратора поверх. Переопределения хранятся в `data_dir/skills_overrides.json`; применяются только поля из `EDITABLE` и `instruction`:

| Поле | Тип | Допустимый диапазон |
|---|---|---|
| `temperature` | float | 0.0–1.0 |
| `max_tokens` | int | 100–32000 |
| `timeout_s` | float | 5–900 |
| `retries` | int | 0–5 |
| `instruction` | str | текст промпта |

  Диапазоны объявлены в `EDITABLE`; их проверка выполняется вызывающим кодом админки, а не в `base.py`.
- `save_overrides(data)` записывает файл и сбрасывает кэш `load_skills`.
- `skill(name)` — спецификация по имени (KeyError, если навыка нет).

Параметры `timeout_s` и `retries` используются слоем моделей: бюджет времени вызова навыка равен `timeout_s × (retries + 1)` (см. [llm.md](llm.md)). Навыки, вызывающие модель, берут `instruction`, `temperature` и `max_tokens` из спецификации.

Все `schema_in.json` сейчас одинаковы и минимальны: `{"$schema": ".../2020-12/schema", "type": "object"}`. Фактический вход определяется сигнатурами функций `run.py`, а выход модели проверяется Pydantic-моделями в коде.

## intake

**Назначение.** Разбор запроса методиста (и выдержки из референса) в параметры программы `Params`.

**Вход.** `run(text, references_text='', stats=None)`; в модель уходит `{"request": text[:5000], "reference_excerpt": references_text[:1500]}`.

**Выход.** `(Params, used_llm)`.

**Как работает.**

1. `parse_numbers(text)` — всегда, без модели: тип программы по ключевым словам («общеразвива», «стажировк», «повышени… квалификац» / «переподготовк»), название в кавычках, нагрузка в день, занятия «по N часа M раз в неделю», часы ИА, объём (наибольшее из чисел с «час»/«ч», без нагрузки в день и неделю и без часов ИА), срок в неделях (месяц = 4.3 недели), форма обучения, признак ДОТ, отсутствие аудиторных занятий, «практика не меньше половины» (доля 0.5), материалы (число вопросов теста, слайды для первых N занятий или для модуля «про …»), форма ИА, признак референса, ограничения («доступны в России», «обезличенные»), ожидание заказчика («чтобы … работ…»). Числительные словами поддерживаются.
2. Если модель доступна — вызов с инструкцией из `SKILL.md`, схема `IntakeLLM` (название, направление, аудитория, входной уровень, форма, форма ИА, обязательные темы, ограничения, ожидание заказчика). Числа из шага 1 имеют приоритет; темы ограничиваются 12, ограничения — 8.
3. Без модели — `_heuristic_semantics`: аудитория по «для …», входной уровень по «без опыта …» / «знают/умеют…», темы по «темы: …», направление — название или первая тема.

## classify

**Назначение.** Тип программы, шаблон АЦР, выдаваемый документ, нормативная база и ПС из реестра (FR-06, FR-07). Модель не используется.

**Вход.** `run(text, params)`. **Выход.** `ClassifyResult(program_type, template, issued_document, norm_base, profstandard, confidence, message)`.

**Правила.**

- Тип из `params.program_type` (уверенность 0.95); иначе «школьник», « класс», «детей», «подростк» → ДООП (0.75); иначе тип не определён и уйдёт в вопрос `clarify`.
- Шаблоны: `dpp_pk` → «ДПП ПК», удостоверение о ПК; `dpp_pk_internship` → «ДПП ПК (стажировка)», удостоверение; `doop` → «ДООП», сертификат.
- Нормативная база — `norm_base_for(type, текст)` из `src/app/kb/registry.py`: обязательные акты типа и акты с ключевыми словами запроса.
- ПС — `pick_ps` по реестру (только для ДПП).

## clarify

**Назначение.** До 5 вопросов только по пустым обязательным полям (FR-11…FR-13). Модель не используется.

Обязательные поля и проверка (`missing_fields`): тип программы, объём, аудитория **и** входной уровень (одно поле `audience`), форма обучения, форма ИА. У каждого вопроса есть варианты ответа.

- `run(params)` → список `Question` (`q1`…`q5`).
- `apply_answers(params, questions, answers)` — ответ ищется по id вопроса или имени поля; пустой ответ равен «На ваше усмотрение». Такое значение берётся из профиля организации (`org_profile()['defaults']`), иначе из встроенных `DEFAULTS` (ДПП ПК, 72 ч, «Взрослые слушатели с базовой компьютерной грамотностью», очно-заочная, «Защита проекта») и записывается в `Assumption` с источником «профиль организации (на усмотрение агента)».
- `fill_defaults(params)` — режим `auto`: все пустые поля заполняются как «На ваше усмотрение».
- `_set` нормализует свободный текст (например, «стаж» → стажировка, «дистан» → дистанционная, цифры объёма).

## skeleton (+ library.py)

**Назначение.** Цель, компетенции с индикаторами «знать/уметь/владеть» и РО, модули и темы с весами и долями видов работы (FR-14, FR-16). Часы модель не считает — их распределяет солвер.

**Вход.** `run(params, program_type, ps, reference_structure, stats, comment='', current=None, org_documents=None, norm_documents=None)`. В модель уходит: тип программы словами, название, направление, объём, аудитория, входной уровень, форма, ИА, обязательные темы (из запроса и `MUST_COVER` направления), ограничения, ожидание заказчика, подсказка по числу модулей (`_module_count_hint`: ≤ 24 ч — 3–4 модуля; ≤ 80 ч — 5–6; ≤ 200 ч — 6–8; больше — 7–10), признак стажировки, ПС с ТФ, структура референса (до 30 строк), комментарий методиста и текущий каркас (возврат с комментарием, FR-24), до 4 фрагментов документов организации и до 4 выдержек НПА.

**Выход.** `SkeletonDraft(title, goal, competencies, modules, source)`, где `source` — `llm`, ключ домена библиотеки или `generic`.

**Постобработка ответа модели** (`_from_llm`): до 8 компетенций (префикс `К` для ДООП, `ПК` для ДПП), до 6 индикаторов, до 3 РО на индикатор; коды РО перенумеровываются (`РО c.n`, id `loc.n`); ТФ сопоставляется `match_tf` (код модели, если он есть в ПС, иначе наибольшее пересечение основ слов, иначе по кругу); до 12 модулей и 8 тем; доли ЛК и СРС ограничиваются диапазоном 0–0.6. Затем `link_outcomes` (каждый РО раскрыт хотя бы в одной теме, у каждой темы есть РО), `drop_assessment_modules` (убирает модули «Итоговая аттестация», «Защита отчёта», «Подготовка к …», если остаётся не меньше двух), `ensure_topics` (обязательные темы направления добавляются в ближайший по смыслу модуль). Каркас модели принимается, если в нём не меньше двух модулей.

**Резерв** (`from_library`). `pick_domain` выбирает домен из `library.py` по ключевым словам (с обязательными словами `requires_any`): `python_school`, `ai_teachers`, `data_analysis`, `cybersecurity`, `devops`. Если домен не найден — `generic_domain`: вводный модуль, по модулю на каждую обязательную тему (до 6) с темами «основные понятия» и «практикум», при проектной ИА — модуль «Итоговый проект», две общие компетенции. `MUST_COVER` задаёт обязательные темы для доменов `devops` (Linux, сети, контейнеризация, CI/CD, мониторинг, IaC) и `data_analysis` (pandas, визуализация, SQL, статистика).

## content

**Назначение.** Содержание одного модуля утверждённого каркаса: рабочая программа (аннотация и тексты тем), тест с ключами, задания семинаров с критериями, планы лекций и слайды, источники, для стажировки — вопросы собеседования (FR-25…FR-29).

**Вход.** `run(doc, module, n_questions, test_id, slide_topics, stats=None, instruction_extra='')`. В модель уходят: программа, шаблон, аудитория и входной уровень, ограничения, модуль с часами и формой контроля, темы (часы, признак практики, коды РО, нужны ли слайды), РО модуля, число вопросов, версии инструментов из реестра, встречающихся в модуле (`_relevant_tools`), до 4 фрагментов документов организации, до 3 выдержек НПА, правила для вопросов (только по темам модуля, без сервисов, недоступных в России), примечание для стажировки или текст правки методиста.

**Выход.** `ModuleContent(program, questions, tasks, lectures, sources, source, interview)`; `source` = `llm` или `template`.

**Постобработка.** `scrub_blocked` отбрасывает вопросы, упоминающие сервисы из `ai_services_blocked`, а в остальном тексте заменяет их на «зарубежный сервис». `_from_llm`: ключ вне диапазона заменяется на 0, недостающие вопросы добираются из резерва, коды РО переводятся в id (по умолчанию — РО темы или по кругу), задания без критериев получают критерии по умолчанию (4 + 4 + 2 балла), лекции — только для тем из `slide_topics` (до 8 слайдов по 6 тезисов, длительность `max(45, lk × 45)` мин, пример кода в `code_examples`), до 3 источников, до 6 вопросов собеседования длиннее 15 символов.

**Резерв** (`fallback`). Аннотация из РО модуля, тексты тем из описаний, контрольные вопросы по темам; вопросы теста: верный ответ — текст РО темы, дистракторы — РО и темы других модулей, позиция ключа чередуется `i % 4`; задания — по одному на тему с практикой (для стажировки на каждую тему) с критериями по умолчанию; лекции — пять типовых слайдов и план по умолчанию. Модули из резерва попадают в `kit.drafts` и в отчёте помечаются «нужна доработка эксперта».

## review_assist

**Назначение.** Предложение правки по комментарию эксперта в пределах его модуля; часы и РО не меняются (FR-41).

- `fragment_of(doc, node_id)` — текст фрагмента: задание, критерий (`task#c2`), вопрос, лекция, пункт плана (`lec#p3`), слайд.
- `propose(doc, module_id, node_id, comment)` — при доступной модели и найденном фрагменте вызов со схемой `Proposal` (`proposal`, `new_text`, `affected`); возвращается только `proposal`. Без модели — шаблон «Учесть замечание эксперта: «…». Правка затронет только этот элемент модуля; часы и РО не меняются.»
- `propose_full` — добавляет список затрагиваемых элементов по графу связей (`descendants` из `workflow.py`).

## repair

Описание в `skills/repair/SKILL.md`, реализация — `src/app/validation/repair.py`. Несмотря на `model_role: judge`, все исправления детерминированные, модель не вызывается. Не больше двух проходов (цикл в `generate_kit`). Подробно — в [validation.md](validation.md).

## validate

Описание в `skills/validate/SKILL.md`: 27 правил, 23 кодом и 4 смысловых (V-21, V-22, V-26, V-27). Код — `src/app/validation/rules.py`, уточнение смысловых правил моделью — `src/app/validation/judge.py` (свой системный промпт, не текст `SKILL.md`). См. [validation.md](validation.md).

## hours_solver

Описание в `skills/hours_solver/SKILL.md`, реализация — `src/app/solver/hours.py` и `src/app/solver/calendar.py`: метод наибольших остатков, практика закрывает строку, режим стажировки — все часы модулей в СРС, детерминированный результат. См. [solvers.md](solvers.md).

## export

Описание в `skills/export/SKILL.md`, реализация — `src/app/export/service.py`. Реквизиты приказа, ФИО и подписи остаются полями. См. [export.md](export.md).

## workflow

Описание в `skills/workflow/SKILL.md`, реализация — `src/app/agent/workflow.py`: конечный автомат `draft → questions → skeleton → skeleton_approved → generating → kit_ready → on_review → on_approval → approved` (возврат — `returned`). Генерация содержания — только после утверждения каркаса методистом или правилом auto-approve. См. [agent-workflow.md](agent-workflow.md).

## Добавление навыка

Новый навык добавляется каталогом `src/app/skills/<имя>/` с `SKILL.md`, схемой и `run.py`: он сразу появляется в `load_skills()`, в списке `GET /api/v1/skills` (имя, описание, версия) и в настройках администратора. Вызов навыка из конвейера добавляется в `src/app/agent/workflow.py`.

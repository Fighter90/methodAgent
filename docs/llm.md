# Слой моделей

Слой моделей — `src/app/llm/client.py` — это клиент шлюза Cloud.ru, написанный на httpx без сторонних SDK, (Cloud.ru Evolution Foundation Models или шлюз хакатона) с моделями GigaChat. Он обслуживает две роли (генерация и судья) с резервной моделью, эмбеддинги для базы знаний организации, повторы с паузами, бюджет времени навыка, общий семафор параллельности, учёт токенов и рублей по навыкам, дневной бюджет и распознавание суточного лимита шлюза. Любая неустранимая ошибка превращается в исключение `LLMUnavailable`, которое навыки перехватывают и переходят на детерминированный резерв, поэтому сбой шлюза не останавливает конвейер. Настройки — в `src/app/core/config.py` (переменные окружения, `.env`, `/opt/hackathon/ai.env`).

## Провайдеры

| `LLM_PROVIDERS` | Поведение |
|---|---|
| `cloudru` (по умолчанию) | Рабочий режим. Модель включена, если задан ключ (`llm_enabled = providers == 'cloudru' and api_key`). |
| `fixtures` | Без сети. `llm_enabled` = false, поэтому навыки сразу идут в резервную генерацию (регулярные выражения, библиотека каркасов, шаблонное содержание); судья не вызывается; `check_source_urls` не ходит в сеть. Отдельных «фикстурных» ответов модели в коде нет — детерминированность обеспечивают резервы навыков. |

Ключ ищется в `LLM_API_KEY` или `CLOUDRU_API_KEY`; адрес — в `LLM_BASE_URL` или `CLOUDRU_BASE_URL` (по умолчанию `https://foundation-models.api.cloud.ru/v1`). Транспорт — собственный HTTP-клиент на httpx (`src/app/llm/gateway.py`), без SDK сторонних провайдеров: клиент создаётся лениво, с таймаутом `llm_timeout_s` и без встроенных повторов (повторы делает сам слой). Режим провайдера можно переключать в админке (`src/app/core/runtime.py`, поле `llm_providers`).

## Модели и тарифы

| Назначение | Настройка | Значение по умолчанию | Цена, ₽ за 1 млн токенов (вход / выход) |
|---|---|---|---|
| Генерация (роль `generate`) | `llm_model_generate` | `GigaChat/GigaChat-3-Pro` | 73.03 / 176.39 |
| Судья (роль `judge`) | `llm_model_judge` | `ai-sage/GigaChat3.5-432B-A28B-Reasoning` | 96.22 / 288.60 |
| Резерв генерации | `llm_model_reserve` | `GigaChat/GigaChat-3-Pro` | как у генерации |
| Эмбеддинги | `llm_model_embed` | `ai-sage/Giga-Embeddings-instruct-3B` | не учитывается (0 ₽) |

Порядок моделей роли (`_models`):

- `generate`: основная → резервная. По умолчанию они совпадают, и тогда в списке одна модель.
- `judge`: судья → модель генерации.

Цена (`_price`) выбирается по имени модели: тариф судьи — для `llm_model_judge`, иначе тариф генерации.

## `complete_json`

```python
await get_llm().complete_json(skill=..., system=..., user=..., schema=PydanticModel,
                              role='generate', temperature=0.2, max_tokens=2000, stats=CallStats())
```

Проверки перед вызовом (каждая — `LLMUnavailable`):

1. модель не включена — «LLM не настроен»;
2. сегодня (по МСК) уже получен ответ «суточный лимит исчерпан» — `LIMIT_MSG`;
3. расход за сутки не меньше `llm_daily_budget_rub` — «Дневной бюджет LLM … ₽ исчерпан».

Цикл по моделям роли:

- **Попытки.** Для модели-судьи — одна попытка (ответ долгий и дорогой), затем резерв. Для остальных — до 3 попыток с паузами 1 и 3 с между ними (`_RETRY_PAUSES`).
- **Бюджет времени навыка.** `timeout_s × (retries + 1)` из `SKILL.md` навыка (`_budget_s`); для имени без `SKILL.md` (например, `judge`, `embed`) — `llm_timeout_s × 3`. Считается только активное время запросов внутри семафора, ожидание очереди не считается. Таймаут одного запроса — `max(5, min(llm_timeout_s, оставшийся бюджет))`. Бюджет исчерпан — `LLMUnavailable`, и навык уходит в резерв.
- **Разбор ответа.** `parse_json` убирает блоки `<think>…</think>` (и оборванный `<think>` без закрытия), обрамление ```` ```json ````, текст до первой `{`/`[` и после последней `}`/`]`, висячие запятые. Затем ответ проверяется Pydantic-схемой.
- **Невалидный JSON или схема.** Если ответ пустой (рассуждающая модель израсходовала лимит), повторяется исходный запрос. Иначе модели отправляются её ответ (до 6000 символов) и текст ошибки (до 800 символов) с просьбой вернуть исправленный JSON; это считается одной из попыток.
- **Ошибки HTTP и сети.**

| Ситуация | Реакция |
|---|---|
| 401, 403 | Сразу следующая (резервная) модель. |
| 429 с признаками суточного лимита (`daily`, `spending limit`, `llm_daily_limit` в тексте или теле ошибки; `is_daily_limit`) | Отметка лимита на сегодня (`_mark_limit`), сразу `LLMUnavailable(LIMIT_MSG)`, без повторов и без резерва — лимит общий для всех моделей шлюза. |
| 429 (перегрузка) | Пауза `15 × (номер попытки + 1)` с (15, 30, 45), затем обычная пауза и повтор. |
| 5xx, таймаут, сеть | Пауза и повтор, затем резервная модель. |

  После всех моделей — `LLMUnavailable('<навык>: модель не ответила (<тип ошибки>)')`.

Модуль-описание в начале файла упоминает, что после 429 параллельность «временно снижается»; в коде такого снижения нет — используется только пауза.

## Параллелизм

- Один семафор `asyncio.Semaphore(max(1, llm_concurrency))` на процесс; судья использует тот же семафор (`_judge_sem = _sem`), потому что шлюз допускает 2 параллельных запроса на команду. По умолчанию `llm_concurrency = 2`.
- Эмбеддинги тоже идут через этот семафор, пачками по 16 текстов.
- Генерация модулей в `generate_kit` запускает `max(4, gen_workers)` задач (по умолчанию `gen_workers = 6`), но к шлюзу одновременно уходят не больше `llm_concurrency` запросов.
- Число одновременных фоновых заданий ограничено `max_parallel_jobs = 4` (`src/app/programs/service.py`).

## Таймауты, повторы и отказы

Внешний вызов модели никогда не висит без ограничения и никогда не роняет конвейер: у каждого запроса есть таймаут, у каждой ошибки — заранее известная реакция, а у каждого навыка — детерминированный резерв.

### Таймауты

| Уровень | Значение | Где |
|---|---|---|
| Запрос httpx | `llm_timeout_s` (120 с), соединение — `min(10, llm_timeout_s)` | `gateway.CloudRuGateway` |
| Один вызов `chat/completions` | `asyncio.wait_for`, `max(5, min(llm_timeout_s, остаток бюджета навыка))` | `complete_json` |
| Пачка эмбеддингов (16 текстов) | `asyncio.wait_for`, `llm_timeout_s` | `embed` |
| Проверочный запрос | `asyncio.wait_for`, `min(30, llm_timeout_s)`, одна попытка | `ping` |
| `timeout_s` навыка | `intake` 30, `skeleton` 60, `content` 120, `review_assist` 30 (см. [skills.md](skills.md)) | `SKILL.md` |
| Бюджет навыка | `timeout_s × (retries + 1)`: `intake` 90 с, `skeleton` 180 с, `content` 360 с, `review_assist` 60 с; судья и эмбеддинги — `llm_timeout_s × 3` | `_budget_s` |
| Проверка ссылок источников | 4 с на адрес, до 8 адресов параллельно | `workflow.check_source_urls` |

Бюджет навыка считает только активное время запросов (внутри семафора), ожидание очереди шлюза не считается. Исчерпан — `LLMUnavailable` без нового запроса, навык уходит в резерв, и сроки FR-19/FR-31 держатся.

### Повторы

| Ошибка | `complete_json` | `embed` |
|---|---|---|
| Сеть, таймаут, 5xx, ответ без `choices`/`data` | до 3 попыток с паузами 1 и 3 с, затем резервная модель роли | до 3 попыток с паузами 1 и 3 с |
| 429 (перегрузка) | пауза 15 × (попытка + 1) с, затем обычная пауза и повтор | так же |
| 429 «суточный лимит» | отметка лимита до 00:00 МСК, сразу `LLMUnavailable`, без повторов и резерва | так же |
| 401/403 | без повторов, сразу резервная модель | сразу `LLMUnavailable` |
| Невалидный JSON / схема | модель получает свою ошибку и исправляет ответ (это одна из попыток) | — |
| Дневной бюджет (`llm_daily_budget_rub`) исчерпан | `LLMUnavailable` до запроса | — |

Судья (модель рассуждений) делает одну попытку на модель, затем резерв. Наружу `complete_json` и `embed` отдают только `LLMUnavailable`.

### Отказы навыков и резервная генерация

Навык ловит только `LLMUnavailable` и `MODEL_DATA_ERRORS` (ответ прошёл схему, но не лёг в каркас: `ValidationError`, `ValueError`, `KeyError`, `IndexError`, `TypeError`, `AttributeError`). Остальные исключения — ошибки кода — не глушатся.

| Навык | Резерв | Запись об отказе |
|---|---|---|
| `intake` | эвристический разбор запроса | `CallStats.fallback('intake', …)` |
| `skeleton` | типовая структура направления из библиотеки | `CallStats.fallback('skeleton', …)` |
| `content` | шаблон модуля из каркаса (тест, задания, планы лекций, слайды), модуль в `kit.drafts` | `CallStats.fallback('content', …, module=…)` |
| `_fix_examples` | неисправимый пример кода убирается из лекции | `CallStats.fallback('content', …)` |
| `review_assist` | шаблонное предложение с текстом замечания | журнал |
| `judge` | остаются оценки правил кодом | `CallStats.fallback('judge', …)` |
| эмбеддинги базы организации | поиск по словам | журнал |

`workflow._stats_to_usage` переносит отказы шага в `doc.step_errors` (`step`, `skill`, `module`, `error`, `fallback`, `at`) и в заметки агента; автопрогон отдаёт их полем `step_errors`.

Страховки конвейера, где намеренно оставлен перехват любого исключения (`# noqa: BLE001` с причиной, `logger.exception` с id программы, шагом и модулем):

- задача одного модуля в `generate_kit` — модуль собирается по шаблону, отказ в `step_errors`, остальные модули и комплект собираются;
- одно из 27 правил автопроверки — правило получает «!» с текстом «Правило не выполнено»;
- автопрогон `POST /programs?mode=auto` — `status: failed`, причина в `agent_notes` и `step_errors` (без текста исключения), а не HTTP 500;
- фоновое задание очереди — `status: failed` с текстом ошибки;
- разбор таблиц PDF сторонней библиотекой — страница без таблиц, текст уже взят.

### Без модели

При `LLM_PROVIDERS=fixtures`, исчерпанном лимите или отказе шлюза комплект собирается полностью по шаблонам: каркас из библиотеки направлений, часы — солвером, тесты и задания — из РО каркаса, слайды хотя бы одного модуля (заказанного, иначе первого с лекциями) — `workflow.ensure_module_slides`.

### Оборванный ответ

Если ответ модели обрывается (лимит токенов или шлюз) и попытки исправления не помогли, навык content (`partial_ok=True`) получает целую часть ответа: `parse_json(salvage=True)` отрезает незаконченный хвост до последнего целого значения и закрывает скобки, а недостающие вопросы, задания и лекции модуль добирает по шаблону. Отказ пишется в `step_errors` как «ответ модели оборван». Остальные навыки частичный ответ не принимают: у каркаса потеря модуля исказила бы часы (SPEC-LLM-24).

## Учёт токенов и стоимости

- `CallStats` накапливает `tokens_in`, `tokens_out`, `cost_rub`, `calls`, разбивку `by_skill` по имени навыка и отказы навыков `fallbacks`. `add` и `merge` выполняются под замком (`threading.Lock`), поэтому один `CallStats` можно передавать в параллельные задачи и потоки.
- Параллельная генерация модулей в `generate_kit` всё же не делит изменяемые данные: у каждой задачи свой `CallStats` и свой результат `ModuleRun`; после `asyncio.gather` результаты сортируются в порядке модулей каркаса и сливаются в комплект и общий `CallStats` последовательно. Прогресс (`module_state`, лента) меняется и отправляется под `asyncio.Lock`.
- После каждого успешного ответа берутся `usage.prompt_tokens` и `usage.completion_tokens`; стоимость `= (вход × цена_входа + выход × цена_выхода) / 1 000 000`.
- В лог пишется навык, модель, токены, задержка и номер попытки; ключ и тексты запросов не логируются.
- `workflow._stats_to_usage` переносит `CallStats` в `doc.usage` (токены, рубли, вызовы, разбивка по навыкам); `quality()` показывает стоимость генерации руководителю.
- Эмбеддинги учитываются в `CallStats` под именем `embed` только по входным токенам, со стоимостью 0.

## Дневной бюджет и суточный лимит

- Сутки считаются по Москве (UTC+3, `_today`), а не по времени контейнера.
- Расход за сутки (`_spend`) и день отметки лимита хранятся в `data_dir/llm_spend.json` (`day`, `rub`, `limit_day`) и переживают перезапуск.
- `llm_daily_budget_rub = 90` ₽ (шлюз хакатона даёт 100 ₽): при достижении порога новые вызовы сразу получают `LLMUnavailable`, и навыки уходят в резерв.
- `limit_reached()` — шлюз сегодня ответил «суточный лимит исчерпан». Тогда `workflow._limit_note` добавляет методисту заметку «Дневной лимит шлюза LLM исчерпан, до 00:00 МСК модули собираются по шаблону…», а судья не запускается.
- Успешный `ping()` сбрасывает отметку лимита раньше полуночи.

## `GET /api/v1/llm/status`

Объявлен в `src/app/main.py`. Делает проверочный запрос `ping()` к модели генерации («Ответь одним словом: ок», `max_tokens=5`) и возвращает:

| Поле | Содержание |
|---|---|
| `enabled` | включена ли модель; при выключенной — ещё `provider` |
| `ok`, `model`, `latency_s` | результат проверочного запроса |
| `error` | тип исключения при неудаче |
| `spent_today_rub`, `daily_budget_rub` | расход за сутки по МСК и бюджет |
| `daily_limit_reached` | отметка суточного лимита |
| `models` | `generate`, `judge`, `embed` |
| `judge_enabled` | `llm_judge_enabled` |

Проверочный запрос не учитывается в расходе.

## Эмбеддинги

`embed(texts, stats=None)` — векторы текстов моделью `llm_model_embed` для базы знаний документов организации (FR-09, `src/app/kb/orgdocs.py`). Каждая пачка ограничена таймаутом и повторяется по правилам из раздела «Таймауты, повторы и отказы» (резервной модели нет); 401/403, выключенная модель или суточный лимит дают `LLMUnavailable` без повторов. Нормативная база знаний (`src/app/kb/norms.py`) эмбеддинги не использует — поиск там по словам.
